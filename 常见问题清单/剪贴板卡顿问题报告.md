## 一、现象与影响面

**现象**：在可编辑文本区选中文字后按 Ctrl+X，界面冻结约 1~2 秒才出现结果；有时选区根本不被删除，粘贴目标里拿到的是**上一次**的剪贴板内容。Ctrl+C、Ctrl+V 与右键菜单的剪切/复制/粘贴同样受影响，复制按钮偶发"无法写入剪贴板"报错。

**判定过程**：Prompt 收藏夹里的编辑区（`UI4CodeEditor`）出现该现象后，先在应用层做了修补；用户自行打开组件库示例工程逐一试验后反馈：

> "撤回你的修复方案，是基本组件的问题？我测试了基本组件涉及到文本可编辑的组件 Ctrl+X 都有问题"

据此把定位从应用挪到组件库。受影响的库内路径（修复前）：

| 控件 | 修复前的实际调用 | 入口 |
|---|---|---|
| `UI4TextBox` | 框架 `TextBox.Copy()/Cut()/Paste()` → `System.Windows.Clipboard` | 快捷键、右键菜单（`UI4TextBox.cs:311-321`） |
| `UI4PasswordBox` | 同上（明文模式）；密码模式仅靠按键拦截 | 快捷键、右键菜单 |
| `UI4CodeEditor` | AvalonEdit `TextEditor.Cut()/Copy()/Paste()` → 内部同样调用 `System.Windows.Clipboard` | 快捷键、右键菜单（`UI4CodeEditor.cs:57-59`） |
| `UI4TextBlock` | `Clipboard.SetText(_textBox.SelectedText)`（`UI4TextBlock.cs` 原 310 行） | 右键复制 |
| `UI4DataGrid` | `Clipboard.SetDataObject(SelectedCellsToString())`；单元格编辑框为框架 `TextBox` | 右键复制、单元格编辑 |

**触发条件**：机器上有常驻剪贴板监听程序（本机为 PixPin，截图 + 剪贴板历史）。没有监听程序时同样的代码通常察觉不到，因此这是"环境相关但必然复现"的缺陷——用户机器上一直开着。

## 二、根因分析

### 2.1 系统层：剪贴板是全局单锁资源

同一时刻只允许一个线程 `OpenClipboard`。任何剪贴板读写（含 OLE 封装）最终都要拿到这把锁。监听类程序为了维护历史，会在每次 `WM_CLIPBOARDUPDATE` 后重新打开剪贴板读取内容（截图工具还要渲染位图/文本快照），单次持锁可达几十到几百毫秒。于是"按键 → 写剪贴板"这条路径会和监听者反复争锁。

### 2.2 框架层：WPF `Clipboard` 走 OLE 通道，且在被调用线程上重试

`System.Windows.Clipboard.SetText/SetDataObject` 不是直接 `SetClipboardData`，而是 `OleSetClipboard` + flush 协议：要把数据"落地"给剪贴板查看器/监听者，就必须打开剪贴板并等待 OLE 刷新完成。抢不到锁时，OLE 层在**调用线程**上重试，最终抛 `CLIPBRD_E_CANT_OPEN`（表现为"无法写入剪贴板"报错）。WPF 可编辑控件的默认 Copy/Cut/Paste 全都落在这条路上，重试期间 Dispatcher 线程被占住 → 整个窗口冻结。实测数值见第五节（框架 `TextBox` 单次 Ctrl+X 阻塞 927ms 且选区未删除）。

关键点：**延不是"剪切逻辑慢"，而是在 UI 线程上等一把被别人占着的锁，并且要等满重试预算才继续。**

### 2.3 AvalonEdit 同属一根因

`ICSharpCode.AvalonEdit.dll` 二进制内可检出 `Clipboard.SetText` / `SetDataObject` / `ContainsText` 的引用，因此 `UI4CodeEditor` 与 WPF `TextBox` 症状完全一致，不是 AvalonEdit 特有问题。

### 2.4 为什么记事本不卡，以及这条路为什么不能照搬

记事本（原生 Win32）用的是**"先取得所有权 + 延迟渲染"**：`OpenClipboard(自己的 hwnd)` → `EmptyClipboard`（瞬间拿到所有权，锁只在调用的一瞬间被持有）→ `SetClipboardData(CF_UNICODETEXT, NULL)` 声明"数据稍后再给" → 立即返回并删除选区；只有粘贴方真正来取数据时系统才发 `WM_RENDERFORMAT`，此刻才现场填内容。抢锁压力因此落在监听者一侧，不在按键路径上。

本机实测该协议**不可用**（独立 net48 程序 + 消息窗口 + 隐藏顶层窗口两种方式均验证）：

- `OpenClipboard(自己的 hwnd)`、`EmptyClipboard`、`GetClipboardOwner` 归属本进程 —— 全部成功；
- `SetClipboardData(CF_UNICODETEXT, NULL)` 固定返回 `NULL`，`GetLastError()` 为 0，之后**从不收到** `WM_RENDERFORMAT` / `WM_RENDERALLFORMATS`；在持锁状态内重试 6 次结果相同；
- 同一窗口、同一锁状态下改为 eager 写入（`GlobalAlloc` + 拷贝 + 真实句柄）则成功，`Get-Clipboard` 可读出；
- 对照：用 SendKeys 对真实记事本发 Ctrl+C，剪贴板所有者是记事本进程且内容可读出。

微软文档另有一处直接对应本问题的提示：`OpenClipboard(NULL)` 后调用 `EmptyClipboard` 会把所有者置空，导致 `SetClipboardData` 失败；并且对"单一格式的小体积文本"官方建议**直接放置数据而非延迟渲染**（延迟渲染的额外开销大于收益）。

**结论**：机制上无法照搬记事本的延迟渲染，可行的目标是把"等锁"从 UI 线程移走，并把通道换成原生 Win32 写入。

## 三、工作流程与两次误判

| 阶段 | 做法 | 结果 |
|---|---|---|
| ① | 应用层新增 `ClipboardHelper`（Win32 原生写入，UI 线程上 10 次 × 20ms 同步重试） | 写入通道正确，但重试仍在 UI 线程 → 正是"约 2 秒延时"本身 |
| ② | 同文件把重试搬到后台线程（30 × 100ms），完成后回投 UI 线程 | 卡顿改善，但修补位置错误（应用层），其他控件仍受影响 |
| ③ | 按计划实现 Notepad 式延迟渲染（`ClipboardOwner`，消息窗口 + `WM_RENDERFORMAT`） | 见 2.4，本机固定失败 → 该文件删除，回退 ② |
| ④ | 用户实测指出"可编辑文本组件都有问题"，要求撤回应用层方案 | 删除 `src/PromptFavorites/Helpers/ClipboardHelper.cs` 与 `EntryDetailView` 的逐控件接管，能力下沉组件库 |
| ⑤ | 组件库第一版接管只加 `CommandBinding` + `PreviewExecuted` | **实测拦不住真实按键**：`UI4TextBox` Ctrl+X 仍阻塞 1990ms 且选区不删 |
| ⑥ | 把接管改到 `PreviewKeyDown`（按键隧道阶段） | 阻塞降到十几毫秒，选区即时删除，内容正确 |
| ⑦ | 归档时复查各控件接管点 | 发现 `UI4PasswordBox` 明文模式只有实例命令绑定（同 ⑤ 的失效路径）→ 抽出可复用的 `TryHandleKey` 补上 |
| ⑧ | 固化验证程序并全量复跑 | 10 个用例全部 PASS（第五节） |

**核心结论（两条，后续同类问题直接照此判断）**

1. 修补位置：缺陷若在多个消费方/多个控件同时复现，根因在共享组件，必须在组件库修复，应用层不打补丁。
2. 接管层次：WPF/AvalonEdit 的剪贴板默认行为**只能靠按键隧道（`PreviewKeyDown`）拦下**；`CommandBinding.PreviewExecuted` 对真实按键无效（只对程序化 `Execute` 有效）。

## 四、解决方案与改动原理

### 4.1 `UI4Clipboard`（公开 API，`src/StartUI4Controls/UI4Clipboard.cs`）

原生 Win32 通道：`OpenClipboard → EmptyClipboard → GlobalAlloc(UTF-16 含终止符) → GlobalLock/Copy/GlobalUnlock → SetClipboardData(CF_UNICODETEXT) → CloseClipboard`，与 Ctrl+C 在 OS 层实际做的事一致，绕开 OLE 的 flush 协议。

| API | 位置 | 语义与理由 |
|---|---|---|
| `TrySetTextAsync(text, onDone)` | `:76` | 后台线程写入，最多 30 次 × 100ms；完成后经 `SynchronizationContext` 回投调用线程回调 `true/false`。UI 线程绝不等锁 |
| `TryGetTextAsync(onDone)` | `:102` | 后台线程读取，10 次 × 50ms；读不到回调 `null`（粘贴场景静默即可） |
| `ContainsText()` | `:60` | 用 `IsClipboardFormatAvailable(CF_UNICODETEXT)` —— **不打开剪贴板**，不参与抢锁，可安全用于 `CanExecute` 与菜单项判定 |

失败提示：写满重试预算后由 `ClipboardCommandTakeover.OnWriteFailed`（`Internal/ClipboardCommandTakeover.cs`）弹一次 `UI4MessageBox`，提示"无法写入剪贴板，请关闭占用剪贴板的程序后重试"。

### 4.2 `ClipboardCommandTakeover`（internal，`src/StartUI4Controls/Internal/ClipboardCommandTakeover.cs`）

两层接管，职责不同：

- `TryHandleKey(TextBox, KeyEventArgs)`（`:24`）：在 `PreviewKeyDown` 隧道阶段判 `Ctrl + C/X/V`，各自带守卫（复制要求有选区；剪切要求非只读且有选区；粘贴要求非只读且 `ContainsText()`），命中即执行原生通道并返回 `true` 供调用方 `e.Handled = true`。框架自带的 OLE 处理因此完全不被触发。
- `MakeBinding(...)` 生成的 `CommandBinding`：仅在程序化执行 `ApplicationCommands.Copy/Cut/Paste` 时生效，作为补充路径保留（不影响按键）。

`Install(TextBox)`（`:51`）与 `Install(TextEditor)`（`:70`）分别挂到控件本身与 AvalonEdit 的 `TextArea`（命令实际在 TextArea 上触发，接管必须挂在同一元素或其祖先）。

### 4.3 各控件的接管点与差异

| 控件 | 接管点 | 说明 |
|---|---|---|
| `UI4TextBox` | 构造函数 `UI4TextBox.cs:165` → `Install(this)` | 右键菜单的剪切/复制/粘贴改为直接调用 `ClipboardCommandTakeover.Cut/Copy/Paste`（`:311-321`），与快捷键同一实现；菜单可用态用 `UI4Clipboard.ContainsText()` |
| `UI4PasswordBox` | `OnPreviewKeyDown` 明文模式分支 `UI4PasswordBox.cs:388` 调用 `TryHandleKey` | 密码模式行为不变：`Ctrl+C/X` 仍被禁止、粘贴走 `PasteClipboard()`（已改原生异步读取）。原先只有实例命令绑定（`:253-255`），属阶段 ⑤ 的失效路径，故本轮补按键隧道 |
| `UI4CodeEditor` | 构造函数 `UI4CodeEditor.cs:48` → `Install(this)`，接管挂在 `TextArea` | 剪切用 `Document.Replace(SelectionStart, SelectionLength, "")`，粘贴回填后显式设置 `CaretOffset`；菜单项 `:57-59` 同实现 |
| `UI4TextBlock` | `InitCustomMenu` 内 `UI4TextBlock.cs:318` → `Install(_textBox)` | 模板内的只读 `TextBox` 负责选中文本，复制菜单项改用 `TrySetTextAsync`（`:311`） |
| `UI4DataGrid` | `PreparingCellForEdit` → `OnPreparingCellForEdit`（`UI4DataGrid.cs:142/183`） | 单元格编辑器由框架生成，准备编辑时给其 `TextBox` 安装接管；右键复制（`:204`）改用 `TrySetTextAsync` |

### 4.4 应用侧（Prompt 收藏夹）

不保留任何剪贴板实现：`Helpers/ClipboardHelper.cs` 与 `Views/EntryDetailView.xaml.cs` 的逐控件命令接管均已删除，编辑区控件本身即 `UI4CodeEditor`（`Views/EntryDetailView.xaml:86`），复制按钮直接调用库 API（`ViewModels/MainViewModel.cs:179`，成功记 `useCount` 并弹 Toast，失败提示留在应用层）。

## 五、实测数据

**复现与度量方法**（`tools/clipboard-lock-check`，命令见第七节）：

1. 子进程 `--hold 1200`：`OpenClipboard` 占住剪贴板 1.2 秒后关闭 —— 模拟监听者持锁窗口；父进程以 `ExitCode` 断言抢锁确实生效。
2. 父进程（WPF，窗口置于屏幕外）内放置 `plain TextBox` / `UI4TextBox` / `UI4CodeEditor` / `UI4PasswordBox(明文)`，聚焦并选中 `bravo`。
3. `keybd_event` 发送**真实** Ctrl+X/C/V，随后 `Dispatcher.Invoke(no-op, ContextIdle)` 返回即视为输入处理完毕，其间耗时 = UI 线程阻塞时长。

## 六、已知边界与风险

1. **内容是异步落板的**。写入在后台线程重试，最长按约 3 秒预算（30 × 100ms）。锁被长时间占用时，粘贴目标与剪贴板历史工具里的这条记录可能滞后出现。UI 反馈（选区删除、Toast、`useCount`）不再等锁，这是有意的取舍。
2. **剪切在锁久占时可能丢文本**。选区立即删除，若后台写满预算仍失败，被剪掉的文本没有去处，仅弹提示。候选改进（未实现）：失败时把文本放回原位并恢复选区。
3. **只支持 `CF_UNICODETEXT`**。不再产出 RTF/HTML/多格式，粘到富文本编辑器里得到纯文本 —— 与原先框架行为相比是取舍而非缺陷，但与"复制选区带格式"的需求不兼容时需注意。
4. **`Ctrl+Insert` / `Shift+Insert` 未接管**，仍走框架通道，在同样环境下仍可能慢。需要时可在 `TryHandleKey` 里按同样的守卫补上这两组键。
5. **粘贴是异步回填**。读取在后台线程进行，若用户在这几十毫秒内移动了光标，文本会插入到新位置；对极快的连续操作属于可感知但概率很低的行为差异。
6. **所有权仍不属于本应用**。`OpenClipboard(IntPtr.Zero)` 不声明所有者（eager 写入路径下这是正确用法，见 2.4 文档提示）；若第三方随后抢走剪贴板，后续粘贴得到的是对方内容，属系统通用行为。
7. **`UI4PasswordBox` 密码模式仍禁止复制/剪切**（保持既有安全语义），仅明文模式获得本次改进。
